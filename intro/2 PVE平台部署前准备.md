# 2 PVE平台部署前准备——把物理主机变成可管理的集群资源


## 概述
在这个项目里，PVE 是整个管理体系的底座。

如果没有 PVE 集群，就没有统一的节点视图，也就没有统一的主机、镜像和资源登记方式。脚本看不到节点，VM 也就无法被纳入平台；平台看不到资源，后面的任何自动化操作都只能靠人工补位。

所以，真正的起点是先把物理主机做成 PVE 节点，再把这些节点组织成一个能被统一发现、统一管理、统一调度的集群。

## 亮点
这一层准备工作的亮点，可以概括成三点。

第一，先建立统一管理面，再谈自动化。脚本不是直接面对一堆离散主机，而是面对一个已经成型的 PVE 集群。这样一来，主机、VM、存储和网络都能在同一套管理语义下被描述。

第二，把“机器能不能用”变成“资源是否已登记”。物理机器不再只是硬件本体，而是被明确成 `Server`、`PVE` 等角色。角色一旦明确，后续脚本就能按角色做判断，而不是靠人工记忆。

第三，把平台准备和业务部署分开。准备阶段只解决“环境是否可运行脚本”的问题，不涉及后续怎么迁移、怎么落盘、怎么恢复。

## 所解决的问题
这套前置准备主要解决两个问题。

1. 资源分散，平台无法统一识别。  
   物理主机如果只是单独装好系统，没有加入集群、没有统一命名、没有统一 SSH/API 访问方式，那么脚本就无法把它当作平台资源来处理。

2. 前置条件不一致，自动化无法稳定启动。  
   一台主机可能已经有 PVE，另一台还没有；一台能 SSH，另一台不能；一台网络配置完整，另一台还停留在出厂状态。只要这些前置条件不统一，脚本每次启动前就要做大量人工判断。

因此，这一层要做的事，本质上是把“离散硬件”变成“标准化集群资源”。

## 为什么要采用 PVE 作为统一管理层
这个项目选择 PVE，不只是因为它是虚拟化平台，更因为它提供了一套适合做统一管理的接口和资源模型。

PVE 把物理主机、VM、集群节点、网络和存储都放进了同一个控制面里。对于脚本来说，这意味着它不需要分别理解每台机器的管理逻辑，只需要面向统一的 PVE 接口去发现、登记和查询资源。

从工程上看，这个选择还有两个好处。

第一，PVE 天然适合做“中心化管理”。主服务器可以作为控制面，其他物理主机作为集群节点接入；脚本只要连接到 Master，就能看到整个集群。

第二，PVE 天然适合做“对象化资源管理”。节点、VM、存储池都能以对象形式被访问，这让后续的初始化、查询、刷新和调度都有了统一入口。

## 从一台物理机器到可用 PVE 节点，需要什么
如果把一台刚拿到手的物理机器变成可供本项目使用的节点，至少要完成下面几件事。

### 1. 安装 PVE
物理主机需要先安装 Proxmox VE。这里的前提不是“它能开机”，而是“它已经具备虚拟化管理能力”。

安装完成后，这台机器就不再只是普通主机，而是一个可加入集群、可被脚本发现、可承载 VM 的 PVE 节点。

### 2. 明确 Master Server
集群里需要有一台可访问的 Master Server 作为统一入口。这个节点负责提供 PVE API 和 SSH 访问，也是 `interactive_runner` 启动后首先连接的对象。



### 3. 加入 PVE 集群
所有需要被管理的 PVE 节点，都应当加入同一个 Datacenter/Cluster。

这样做的目的很直接：让 `interactive_runner` 可以通过集群视图发现节点，而不是对每台机器单独做离线登记。对脚本来说，集群是资源发现的前提，不是后置优化。

### 4. 统一 SSH 和 PVE API 访问
脚本在启动时不仅要看得见节点，还要能连得上节点。

因此，Master 和各个 PVE 节点都需要准备好：

- 可访问的 SSH 地址
- 可用的 SSH 用户名和密码
- 可访问的 PVE API 用户名和密码
- 固定的 API 端口和验证策略

在项目的默认配置里，这些信息会和 `config.yaml`、`interactive_runner.py` 中的初始化逻辑配合使用。

### 5. 统一节点命名和角色
节点进入集群之后，还需要有清晰的角色定义。

本项目里，节点一般会被区分为两类：

- `Server`：负责控制面、中心管理和资源中转
- `PVE`：作为可调度的机器人主机节点

角色一旦明确，后续的资源登记就有了语义基础。脚本看到的是角色，而不是一串模糊的 IP。

## 为什么网络准备必须放在最前面
PVE 节点要能进集群，网络一定要先准备好。

这里的网络准备，不是指某一次操作时的临时切换，而是指物理主机在加入集群之前，就已经有了稳定的管理网、固定的地址规划和可识别的接口命名。

对这个项目来说，至少要准备三件事。

第一，管理地址要稳定。脚本需要通过 SSH 和 API 连到节点，所以节点 IP 不能随意漂移。

第二，接口命名要清楚。项目里对有线和无线网络都有约定，相关模板放在 [configs/interface.wired](D:/Code/Finecycle/configs/interface.wired) 和 [configs/interface.wireless](D:/Code/Finecycle/configs/interface.wireless)。

第三，网络参数要可推断或可兜底。`interactive_runner` 在启动时会尝试读取节点网络信息，并结合 `config.yaml` 里的默认值补齐 `gateway`、`prefixlen` 和接口名等字段。  
如果这些信息一开始就混乱，脚本虽然可能还能启动，但后续的自动识别会变得不稳定。

换句话说，网络不是后面补上的配置，而是平台能不能被脚本接管的前提。

## 为什么存储也要提前统一
除了网络，存储也是 PVE 平台能不能正常工作的关键。

在这个项目里，平台会默认依赖一套明确的存储语义。比如，集群中应当能识别共享存储和本地存储，资源名称也尽量保持一致，避免不同节点上各自一套叫法。

这样做的原因很简单：脚本需要依赖统一存储视图来理解资源，而不是在每台机器上重新猜测“这块盘叫什么”“这块盘是不是项目要的那种盘”。

因此，在正式运行脚本之前，至少要确认：

- 集群中的共享存储已经准备好
- 本地存储命名与项目约定保持一致
- 各节点能在 PVE 控制面里看到一致的存储资源

这一步不涉及具体的迁移动作，只是把底层资源摆成脚本能稳定识别的形态。

## 为什么要先完成资源登记
当 PVE 集群、网络和存储都准备好之后，下一步不是立刻执行业务流程，而是先把平台资源登记进系统。

在实现上，这个动作主要由 [interactive_runner.py](D:/Code/Finecycle/interactive_runner.py) 负责。它启动后会先连接 Master Server，再扫描集群节点，然后把节点和 VM 纳入 `DataCenter` 的资源视图。

这一步很关键，因为它把“集群里真实存在的东西”变成“系统里能被查询和管理的对象”。

这里可以把它理解成三层对应关系：

1. 物理机先变成 PVE 节点
2. PVE 节点再变成平台资源
3. 平台资源最后才变成脚本可操作对象

如果没有这一层，后面的脚本即使能启动，也只是一个没有上下文的空壳。

## 为什么要准备好 VM 镜像登记
除了节点本身，平台里还需要有可识别的 VM 镜像。

本项目把 VM 作为镜像的载体来管理，所以在开始运行脚本之前，至少要有一批已经存在的 VM，且能够在初始化阶段被注册成镜像对象。这样，系统才能知道每个逻辑镜像对应哪台 VM、位于哪个节点上。

换句话说，平台不是从“没有镜像”开始工作的，而是从“已有 VM 并完成登记”开始工作的。

如果这一步没做，脚本虽然能连接集群，但没有可管理对象，后续的所有自动化入口都无法真正展开。

## 启动脚本前的检查清单
在真正运行 `interactive_runner` 之前，建议按下面的顺序做一次检查。

1. 确认 Master Server 已安装 PVE，并且可以通过 SSH 和 PVE API 访问。
2. 确认所有需要纳入管理的物理主机都已安装 PVE，并加入同一集群。
3. 确认节点 IP、主机名和角色已经统一，不会出现脚本无法识别的情况。
4. 确认网络参数已经准备好，包括有线/无线接口名、网关和 CIDR 信息。
5. 确认存储资源已经统一，至少能被集群一致识别。
6. 确认已有 VM 可以被注册成镜像对象。
7. 确认 `config.yaml` 中的默认值和实际环境不冲突。

如果这些条件都满足，脚本启动后就不会再停留在“环境识别”这一步，而是可以直接进入平台资源管理。

## 小结
这一篇讲的不是迁移本身，而是迁移系统成立之前的前置条件。

简单说，PVE 平台要先搭起来，物理机器要先变成集群节点，网络和存储要先统一，资源和镜像要先登记，脚本才有资格开始工作。

所以，这一层准备的本质，是把“我有几台机器”变成“我有一个可以被系统接管的 PVE 集群”。只有到了这一步，后面的自动化部署、资源管理和状态查询才真正有意义。
